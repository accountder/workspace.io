## 起因：一眼看不出量级

每个月做发票统计，都要打开电子税务局的「全量发票查询」，设好日期区间，点查询，然后盯着页面上一行小字：

> 合计金额：1234567.89 元　合计税额：123456.78 元

问题不在于这个数字难算，而在于**它没法一眼判断量级**。1234567.89 是 123 万还是 12 万？我得先在脑子里除一万，还容易点错小数点。查一个季度还好，碰上要按季度拆开跑四次、再手工累加的时候，这种「看一眼就得换算」的低效会累积成一整天的烦躁。

更烦的是全年查询有单次返回条数上限，直接查一年可能被截断。所以真实流程是：手工改四次日期 → 点四次查询 → 抄四个汇总值 → 相加。中间任何一个数字抄错，后面全错。

于是写了这个插件，叫 **TaxTally**（`tally` 就是合计、记账）。核心逻辑简单到不值一提：把合计金额除以一万，**显示在原数字上方**。但做完之后发现，真正花时间的全在别的地方。

## 它到底做了什么

插件是标准的 Manifest V3 扩展，只对 `*.hubei.chinatax.gov.cn` 注入脚本，一共六件事：

**万元浮层（核心）**。在原数字上方叠一层红色数值，`1234567.89 元` 上面出现 `123.4568 万元`。超过 1 亿自动换成亿元。小数位、颜色、字号、加粗都能调，鼠标悬停能看到精确到分的原值，点一下可复制。

**阈值高亮**。合计金额超过设定值（默认 30 万）时，原始数字变红，回落到阈值以下自动恢复。另外可以单独高亮「数电发票（增值税专用发票）」这类单据行。

**定时刷新**。只对 `/loginb/` 登录页生效——开票、填单的页面一律不刷，免得打断正在填的表单。

**批量汇总**。选年份 + 按季（4 段）或按月（12 段），点一次自动跑完：填日期 → 点查询 → 等汇总稳定 → 读值 → 累加，结果以浮层表格实时显示，一键导出 CSV。

**快捷菜单**。悬浮在右上角，自动填充、身份切换、复制开票、蓝字开具、红字开具等入口。

**设置面板**。四个标签页，顶部实时回显当前页状态和识别到的合计金额。

功能说完了。下面是我认为更有价值的部分——做的时候踩的坑，以及为什么某些设计不能偷懒。

## 一个关键决定：绝不改原数字

最省事的实现方式显然是直接把页面上的文本替换掉：

```js
el.textContent = (num / 10000).toFixed(4) + '万元';
```

但这个方案有个致命问题：**那行数字是页面的数据源，不是静态文案**。

发票查询页是 Vue 3 生产构建的 SPA。汇总数字由组件状态渲染，你改了 DOM 文本，下一次任何响应式更新都会把它覆盖回去，浮层就闪没了。更严重的是，页面上的「复制」「导出」以及后续查询读的是同一份数据，篡改 DOM 会让这些功能拿到错误的值——本来只想改显示，结果污染了数据。

所以做法是**纯视觉叠加**：在数值节点的父容器里插一个绝对定位的浮层，`bottom: 100%`，完全不参与原有布局。

```js
parent.style.position = 'relative';
overlay.style.cssText = 'position:absolute;bottom:100%;left:0;';
```

代价是需要处理重渲染。Vue 更新时会清掉我插入的节点，所以挂了个 `MutationObserver` 监听汇总区域，节点消失就重插。观察器做了 200ms 节流，否则页面高频更新时回调会被打爆。

另外一个细节：最初我用的是普通文档流插入，结果直接把汇总行撑高了——那个汇总区本身只有 48px 高，插一行进去行高立刻变形，整个表格跟着往下跳，视觉上很难受。改成绝对定位后才彻底不占位。

## 踩过的四个坑

### 坑一：后台标签页的定时器根本不准

定时刷新第一版用的是页面内 `setInterval`。在自己的标签页里测一切正常，切到别的标签页去干活，再回来发现它远远没按设定时间执行——间隔设了多久都不对。

原因是 Chrome 对后台标签页的定时器有密集节流策略，间隔会被拉长到最快一分钟一次。实测：一个 500ms 的定时器，在后台标签页 10 秒内只跑了 6 次（正常应该是 20 次）。这意味着**只要标签页不在前台，所有基于页面定时器的方案都不可靠**。

要彻底解决得加一个 background service worker 配 `chrome.alarms`，由扩展层驱动，不受页面生命周期影响。我目前的折中方案是用 `MutationObserver` + `visibilitychange` + `scroll` 补触发，把「不准」的窗口压缩到可以接受的范围，并在文档里如实写明这个限制——而不是假装它能准时。

### 坑二：外链安全 SDK 会吞掉 `<a>` 的点击

这个坑花了最多时间，因为它表现得像「按钮坏了」，但排查方向和真实原因完全错位。

需求很简单：发票查询页跳到了另一个子域（`dppt.xxx`），那边没有快捷菜单，加个「返回」按钮。第一版就是最朴素的一行：

```html
<a href="https://etax.xxx:8443/loginb/">← 返回</a>
```

点了没反应。排查过程：

1. 元素存在、位置正确、`z-index` 是最大值 —— 没问题
2. `document.elementFromPoint()` 命中的就是它自己 —— 没被遮挡
3. 挂监听记录真实鼠标点击 —— **`defaultPrevented: true`，导航事件 0 个**

也就是说，点击被页面拦住了，而且拦完之后它自己也不跳。顺着这条线继续挖，发现页面装了外链安全 SDK：它接管了所有 `<a>` 的点击，`preventDefault()` 之后把 `href` 改写成 `?6eMrZlPH=<几千字符的令牌>`，然后什么都不做。

更糟的是连带现象：一次物理点击，我在 `window` 上记录到 **10 次 click 事件**。叠加令牌化逻辑后，渲染进程 CPU 跑到 111%，主线程整个卡死——截图超时、JS 求值超时、连 `Page.setWebLifecycleState('active')` 都救不回来，只能重新加载页面。所以当时「点什么都没反应」不只是按钮的问题，是页面自己把渲染进程玩死了。

解决方案是**不要用 `<a href>`**：

```js
const el = document.createElement('div');   // 没有 href，SDK 的链接扫描不认
el.setAttribute('role', 'button');

function goHome(e) {
  const el = e.target.closest('#plugin-home');
  if (!el) return;
  e.preventDefault();
  e.stopImmediatePropagation();
  location.assign(HOME_URL);   // 程序化跳转，preventDefault 拦不住
}

['pointerdown', 'click'].forEach(t =>
  window.addEventListener(t, goHome, true)   // 捕获阶段，早于页面自己的处理器
);
```

三个要点缺一不可：元素不带 `href`（避开 SDK 识别）、在 `window` 捕获阶段拦截并用 `stopImmediatePropagation()`（页面在 `document` 上挂了 13 个点击监听器，必须比它们早）、用 `location.assign()` 主动跳转（`preventDefault()` 只能取消**默认行为**，取消不了你主动执行的导航）。

改完之后，导航事件里能看到 `frameRequestedNavigation reason=scriptInitiated`，落地正常。同样的点击，旧实现是 0 个导航事件。

### 坑三：调试工具的鼠标事件对非激活标签页无效

排查上面那个问题时，我用 CDP（Chrome DevTools Protocol）的 `Input.dispatchMouseEvent` 模拟点击，结果 `window` 上的捕获计数一直是 0。第一反应是「元素被遮挡了」，于是花了不少时间在 `z-index` 和 `pointer-events` 上打转。

真相是：**CDP 的输入事件只对当前激活的标签页生效**，非激活标签页根本不会派发。必须先 `Target.activateTarget` 把页面切到前台，否则你测到的「点击无反应」跟代码一点关系都没有。

这个坑很隐蔽，因为 `Runtime.evaluate` 是能正常执行的，只有输入类方法会静默失效。

### 坑四：`_` 开头的目录会让整个扩展加载失败

打包备份时我顺手在扩展目录里建了 `_bak/` 放旧版本文件。结果 Chrome 直接拒绝加载，报：

```
Cannot load extension with file or directory name _bak.
Filenames starting with "_" are reserved for use by the system.
```

Chrome 规定扩展目录内任何以 `_` 开头的文件或目录都是系统保留名（`_locales` 除外）。这个规则很硬，跟代码对不对完全无关。备份应该放在扩展目录**外面**。

## 关于隐私，说点不好听的

这个插件不做任何网络请求，没有统计、没有远程代码。所有设置存在 `chrome.storage`，页面数据一个字节都不出浏览器。

但有一个功能我必须主动交代：**「自动填充」会把信用代码、手机号、密码存进 `chrome.storage.local`**。

`chrome.storage.local` 是未加密的本地存储。任何能读你磁盘文件的程序，都能读到那个值。我把它做成「你点了才生效」，在 README 和隐私政策里用加粗写明，但**这仍然是个设计缺陷**——一个正确处理方式应该用 `chrome.storage.session`（关浏览器即清），或者干脆不落盘。

开源之后这一点大概会被人挑刺，而且挑得对。所以我把它的现状、风险、以及怎么规避（点「重置账号」清空）都写进了文档，而不是藏在代码里。

## 安装

仓库是开源的，MIT 协议：

```bash
git clone https://github.com/accountder/tax-tally.git
```

打开 `chrome://extensions`（Edge 是 `edge://extensions`），右上角开启开发者模式，点「加载已解压的扩展程序」，选包含 `manifest.json` 的目录。然后进电子税务局的发票查询页查一次，就能看到红色万元浮层。

如果别的省份想用，一般改三处：`manifest.json` 的域名、`content.js` 里承载「合计金额」的容器选择器、快捷菜单的入口地址。抓不到数它不会瞎猜，会静默跳过。

## 最后

这个插件的价值大概不在代码本身——四个文件加起来不到两千行，核心换算就是除以一万。真正花时间的是那些「看起来应该很简单」的部分：Vue 页面里怎么插不打扰的浮层、安全 SDK 为什么吞点击、后台定时器为什么不听话、以及一个 `_` 开头的文件夹为什么能让整个扩展报错。

把这些写下来，主要是因为我自己在排查时翻了很多文档和 issue，结论散落在各处。如果后来人遇到「CDP 点了没反应」或者「扩展莫名加载失败」，希望这篇能让他们少绕两个小时。
